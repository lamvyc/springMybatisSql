# 阶段 4：回表与覆盖索引

> 目标：理解二级索引里到底存了什么、为什么“查不全列”要回表，
> 以及怎么用“覆盖索引”让查询只扫索引不碰表。
>
> 配套脚本：`sql/04_回表与覆盖索引.sql`；业务接口：`GET /api/index-demo/products?categoryId=37&mode=all|light`

## 4.1 先建一个正确的“内存模型”

InnoDB 的表有两套结构：

```
┌─────────────────────────────────────────────────────────┐
│ 主键索引（聚簇索引）= 表的正文                              │
│   叶子页里存着【完整的一行】                                │
│   按主键 id 排序                                          │
└─────────────────────────────────────────────────────────┘
┌─────────────────────────────────────────────────────────┐
│ 二级索引（如 (category_id, status, price)）= 另排的目录     │
│   叶子页里只存【索引字段 + 主键 id】  ← 重点！               │
│   不存 product_name、create_time 等其它列                  │
└─────────────────────────────────────────────────────────┘

查询想返回“索引里没有的列”时：
   二级索引找到 (索引字段, 主键id)
       → 拿主键 id 回聚簇索引取完整行   ← 这个动作叫【回表】
```

所以一句话：**二级索引天生“列不全”，要用到列不全就回表；一次回表 = 一次主键随机 IO。**

## 4.2 问题：商品列表接口

```sql
SELECT ... FROM mall_product
WHERE category_id = 37 AND status = 1     -- 一个分类下“上架”的商品
ORDER BY price DESC
LIMIT 20;
```

分类 37 上架商品共 847 个（真实数据）。数据库先给“最懒的写法” `SELECT *`。

## 4.3 第 1 步：无索引 = 全表扫 + 自己排序

```sql
EXPLAIN SELECT * FROM mall_product
WHERE category_id = 37 AND status = 1
ORDER BY price DESC LIMIT 20;
```

真实结果：`type = ALL, rows ≈ 199455, Extra = Using where; Using filesort`
（20 万商品全扫一遍，再给结果排序。）

## 4.4 第 2 步：建联合索引 (category_id, status, price)

```sql
CREATE INDEX idx_cat_status_price ON mall_product (category_id, status, price);
```

再看同一句：

```
type = ref   key = idx_cat_status_price   rows = 847
Extra = Backward index scan
```

✅ 三个条件全被索引吃掉：等值定位到 847 行；price 在索引里有序，
倒着读 = `ORDER BY price DESC`，filesort 消失（`Backward index scan`）。
⚠️ **但 Extra 里没有 `Using index`** —— 意味着 MySQL 只用了索引“定位”，
要返回的 `product_name`、`create_time` 索引里没有，**每一行都要回表去取**。

> 注意：EXPLAIN 里没有“回表”两个字。回表是**动作**，EXPLAIN 不会直接打印。
> 判断方法就是看有没有 `Using index`（下面 4.5 你会看到它出现/消失）。

再验证一件事：**只要有一个列不在索引里，回表就跑不掉。**
就算列表只想要 4 个字段，其中 `stock` 不在索引里：

```sql
EXPLAIN SELECT id, category_id, price, stock FROM mall_product
WHERE category_id = 37 AND status = 1
ORDER BY price DESC LIMIT 20;
-- Extra = Backward index scan（没有 Using index）→ stock 仍需回表
```

## 4.5 第 3 步：把 stock 也塞进索引 → 覆盖索引

```sql
DROP INDEX idx_cat_status_price ON mall_product;
CREATE INDEX idx_cat_status_price_stock ON mall_product (category_id, status, price, stock);
```

**只查索引里有的列：**

```sql
EXPLAIN SELECT id, category_id, price, stock FROM mall_product
WHERE category_id = 37 AND status = 1
ORDER BY price DESC LIMIT 20;
```

真实结果：

```
type = ref   key = idx_cat_status_price_stock   rows = 847
Extra = Backward index scan; Using index     ← 多出来的 Using index 就是“覆盖索引”
```

`Using index` = 需要的所有列在索引里就能拿到，**一次表都不用回**。
（为什么 id 也免费？二级索引叶子自带主键，所以主键永远被“覆盖”。）

**同一张索引，只要 SELECT *，立刻回表：**

```sql
EXPLAIN SELECT * FROM mall_product
WHERE category_id = 37 AND status = 1
ORDER BY price DESC LIMIT 20;
-- Extra = Backward index scan（没有 Using index）→ product_name/create_time 要回表
```

**覆盖 vs 回表，一张图看懂：**

```
覆盖索引（Using index）
   索引页 ──► (category_id,status,price,stock,id) 全在这
   需要：id/category_id/price/stock        ✅ 不碰表

不是覆盖（回表）
   索引页 ──► (category_id,status,price,id)
   需要：product_name/create_time...        ❌ 每行拿 id 回聚簇索引取整行
```

## 4.6 进阶彩蛋：统计接口也能“只扫索引”

```sql
EXPLAIN SELECT category_id, COUNT(*) c, ROUND(AVG(price),2) avg_p, SUM(stock) s
FROM mall_product GROUP BY category_id;
```

真实结果：`type = index, rows ≈ 199455, Extra = Using index`

category_id / price / stock / 主键全在索引里 → 统计直接扫索引完成，不碰表。
（`type=index` 是“扫全索引”，比全表扫省去回表，常出现在聚合/覆盖场景。）

## 4.7 为什么别随手 SELECT *？（真实业务教训）

```
SELECT * 意味着“我要这一行的每一个列”
   → 任何二级索引都装不下“每一个列”
   → MySQL 只能：先用索引定位 → 对每个命中行回表取整行
命中 1000 行 = 1000 次回表 = 1000 次主键随机 IO

行数少时（几百行）感觉不到；行数大 / 表宽（几十列、TEXT/JSON）时，
回表的 IO 量会直接拖垮接口 —— 这是生产慢 SQL 的高频元凶之一
```

**日常规范**：列表/分页查询按需列出展示列，既是流量优化，也给了“覆盖索引”发挥空间；
覆盖索引也只加给高频查询，别为省一次回表把十几个列都塞进索引（索引会臃肿）。

> 小知识：Extra 里另一种写法 `Using index condition`（索引条件下推/ICP）不是覆盖，
> 而是“把部分 where 判断下推到索引层做”，两者别混。覆盖看 `Using index`。

## 4.9 阶段小结

**我学会了什么**
- InnoDB 二级索引叶子只存“索引字段 + 主键”，列不全就要回表（拿主键回聚簇取整行）；
- `Extra` 出现 `Using index` = 覆盖索引 = 不用回表（注意不是 `Using index condition`）；
- `SELECT *` 强制回表：列表查询要按需取列；覆盖索引只加给高频查询。

**日常开发怎么用**
- 列表 SQL 写“要展示的列”而不是 `*`，然后看看 EXPLAIN 能不能凑出覆盖索引；
- 想验证有没有回表：EXPLAIN 看 Extra 有没有 Using index；
- 别为了覆盖硬塞一堆列进索引——索引有体积和维护成本。

**面试怎么答**
- Q：什么是回表？→ 二级索引不含全部列，拿到主键后再回主键索引取整行。
- Q：什么是覆盖索引？→ 查询所需列全部包含在索引里，EXPLAIN 显示 Using index，不用回表。
- Q：为什么建议少用 SELECT *？→ 强制回表更多列、IO 放大、也断送了覆盖索引的可能。

**一句话记忆锚点**：`二级索引只带“字段+主键”，拿不到全列就得回表；EXPLAIN 看到 Using index = 不回了。`

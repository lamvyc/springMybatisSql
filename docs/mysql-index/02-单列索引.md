> ③ 索引为什么能提高查询速度？ ④ 为什么索引不是越多越好？

## 2.1 知识地图

```
单列索引（本阶段，L1 必须掌握）
├─ 建在哪个字段？ → 区分度(cardinality)决定
├─ 三种形态       → 主键索引 / 唯一索引 / 普通二级索引
├─ 为什么快       → B+树：全表扫 O(N) → 树定位 O(logN)
└─ 为什么不是越多越好 → 空间 + 写放大（本阶段用真实数字）
```

## 2.2 问题①：什么字段适合建索引？——用“区分度”说话

不是所有 WHERE 条件都该建索引。两个实验对比。

**实验 A：高区分度列 phone（30 万里几乎一个值）**

```sql
CREATE INDEX idx_user_phone ON mall_user (phone);

EXPLAIN SELECT * FROM mall_user WHERE phone = '13713529579';
```

本机真实输出：

```
type = ref   key = idx_user_phone   rows = 1
```

30 万行里找 1 行 → 索引高效命中。

**实验 B：低区分度列 status（全表只有 5 种取值）**

先看真实分布（本机实测，100 万行订单）：

```sql
SELECT status, COUNT(*) AS cnt FROM mall_order GROUP BY status;
-- status 0: 100043 | 1: 500471 | 2: 99928 | 3: 99796 | 4: 199762
```

再给 status 建索引，看 MySQL 愿不愿意用：

```sql
CREATE INDEX idx_order_status ON mall_order (status);

EXPLAIN SELECT * FROM mall_order WHERE status = 1;   -- 已支付，占 50%
```

本机真实输出：

```
type = ref   key = idx_order_status   rows = 498125
```

`rows=49.8 万`！索引“被用了”，但等于把表一半的行都翻出来——如果还 `SELECT *`，
每一行都要回表做一次随机 IO，**经常比全表顺序扫更慢**。

```sql
EXPLAIN SELECT * FROM mall_order WHERE status = 0;   -- 待支付，实际 10 万行
-- rows ≈ 203490（EXPLAIN 是统计估算，跟实际 100043 有偏差属正常，量级都是“几十万”）
```

**原因（一句话）**：索引的价值是“把大海捞针变成定位”。`status` 这种列一捞就是半张表，
索引解决不了问题，本质是**区分度低**（可选值太少）。

> 所以面试常问的“为什么不对性别/状态这种列建索引”答案是：
> 区分度太低，走索引要回表大量行，优化器经常直接选全表扫，索引形同虚设。

**日常判断公式**：区分度 ≈ 不同值个数 / 总行数，越接近 1 越值得建。

## 2.3 问题②：CREATE INDEX 怎么写？三种索引形态

**建表时的两种“自动索引”** + 我们手建的二级索引，一张表里你都会看到：

```sql
-- 形态 A：主键索引（建表 PRIMARY KEY 自动生成；InnoDB 表数据按它组织）
EXPLAIN SELECT * FROM mall_user WHERE id = 137;
-- type = const, key = PRIMARY, rows = 1      ← 按主键等值查，理论最快
EXPLAIN SELECT * FROM mall_user WHERE id BETWEEN 100 AND 200;
-- type = range, key = PRIMARY, rows = 101    ← 范围扫，定位起点后顺序取

-- 形态 B：业务唯一索引（建表 UNIQUE KEY 自动生成，如 username/order_no）
EXPLAIN SELECT * FROM mall_user WHERE username = 'user_123';
-- type = const, key = uk_username            ← 唯一索引等值 = 最多 1 行

-- 形态 C：普通二级索引（我们手写的 CREATE INDEX，如 phone）
EXPLAIN SELECT * FROM mall_user WHERE phone = '<你的号码>';
-- type = ref, key = idx_user_phone           ← 允许重复，可能返回多行
```

**CREATE INDEX 语法模板（务必记住）**：

```sql
CREATE INDEX 索引名 ON 表名 (列名);          -- 普通索引
CREATE UNIQUE INDEX 索引名 ON 表名 (列名);    -- 唯一索引（列值不许重复）
ALTER TABLE 表名 DROP INDEX 索引名;           -- 删索引
SHOW INDEX FROM 表名;                        -- 看一张表都有哪些索引
```

**type 访问类型总排序**（面试背这个）：

```
const(唯一等值) > ref(索引等值) > range(索引范围) > index(扫全索引) > ALL(全表扫)
```

## 2.4 为什么索引能提高查询速度？（机制图）

```
没有索引（全表扫）                        有索引（B+树）
┌─────────────────────────┐             ┌──────────────────────────┐
│ 第 1 行  phone? 比对      │ 30万次      │        [根节点] 定位起点    │
│ 第 2 行  phone? 比对      │ ──────►    │          ↓  二分          │
│  ...                    │            │   [内部节点] 折半比较       │
│ 第300000行 phone? 比对    │            │          ↓  3~4 层        │
└─────────────────────────┘             │   [叶子页] phone 有序      │
                                        │   顺着叶子链表取出目标行      │
                                        └──────────────────────────┘
  每次都要翻盘、全量比较                    一次定位：O(logN)，只读几个页
```

MySQL 页默认 16KB，一次磁盘 IO 能读一整页。全表扫 = 把 30 万行所在的页几乎全读一遍；
走索引 = 从根到叶子读约 3~4 页 + 回表 1 页。这就是为什么 `rows` 从 30 万变 1。

> B+ 树内部细节（节点分裂/页大小/扇出）属于 L3，面试问“为什么 B+ 树”时能说：
> “矮胖、扇出大，3~4 层就能覆盖千万行；叶子有序链表让范围查询天然高效”即可。

## 2.5 为什么索引不是越多越好？（真实数字）

用订单表（100 万行）现场量一量索引占的空间：

```sql
SELECT table_name,
       ROUND(data_length  / 1024 / 1024, 1) AS 数据_MB,
       ROUND(index_length / 1024 / 1024, 1) AS 索引_MB
FROM information_schema.tables
WHERE table_schema = 'sql_learning_platform'
  AND table_name = 'mall_order';
```

本机实测（MySQL 8.0.46）：

| 索引状态 | 数据 | 索引占用 |
|---------|------|---------|
| 只有主键 + 订单号唯一索引 | 62.6 MB | 26.6 MB |
| 再加 2 个联合索引 | 62.6 MB | **78.7 MB** |

也就是说，**每多建一个联合索引，光磁盘就要多占约 26MB**（100 万行时），
而这只是索引的第一重成本。更贵的成本是：

```
INSERT / UPDATE / DELETE 一行
   → 除了改表本身，还要同步维护【每一个】索引的 B+ 树
   → 索引越多，一次写入要更新的树越多  =  写放大
   → 写入性能随索引数量明显下降；索引还要占内存/磁盘、增加维护负担
```

**什么时候别急着加索引**：
- 写入远多于查询的表（日志、流水），每个索引都是写入的负担；
- 只有几千行的表（全表扫本来就 1ms 内，索引纯浪费空间）；
- 区分度低的列（2.2 已证）；
- 已经有一个能覆盖它的联合索引前缀（阶段 3 讲）。

## 2.6 阶段小结

**我学会了什么**
- 值越分散（区分度高）+ 查询越频繁的列，越值得建单列索引；
- 主键索引自动有且唯一；唯一索引保证业务唯一；二级索引是“另排的目录”；
- type 排序：const > ref > range > index > ALL，EXPLAIN 先看 type；
- 索引 = 空间换时间：快是有代价的（空间 + 写放大），不是越多越好。

**日常开发怎么用**
- 建索引前先跑 `SELECT COUNT(DISTINCT col) / COUNT(*)` 大概估区分度；
- 低频查询、写多表、小表不建；索引命名 `idx_表_列`，方便 SHOW INDEX 排查；
- 上线 DDL 前先 EXPLAIN 旧 SQL + 新 SQL，对比 rows 确实下降再执行。

**面试怎么答**
- Q：索引为什么快？→ 排序结构（B+树）把全表扫描的 O(N) 变成 O(logN) 定位，还有序结构支持范围/排序。
- Q：什么列适合建索引？→ 高频查询 + 区分度高；状态/性别这种低区分度列不适合。
- Q：索引越多越好吗？→ 不是：写放大 + 空间成本 + 优化器选择变复杂；优先满足真实高频查询。

**一句话记忆锚点**：`单列索引 = 给高频且不重复的 WHERE 条件列建“目录”；目录也要维护，别贪多。`

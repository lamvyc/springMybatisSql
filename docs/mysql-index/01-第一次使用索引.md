## 1.2 问题：后台“按手机号查用户”为什么有时快有时慢？

**业务背景**：客服在后台输入手机号查用户资料（登录风控、客诉处理都要用）。
对应的真实 SQL：

```sql
SELECT * FROM mall_user WHERE phone = '13713529579';
```

这是典型的 **WHERE 等值查询**。问题来了：`mall_user` 有 30 万行，
MySQL 怎么从 30 万里找出这一行？

先取一个真实存在的号码备用（每人造数不同）：

```sql
SELECT id, username, phone FROM mall_user ORDER BY id LIMIT 5;
-- 教程全程用 13713529579 举例，请替换成你查到的那一个
```

## 1.3 操作①：先不建索引，直接查（看 MySQL 最笨的查询方式）

```sql
SELECT * FROM mall_user WHERE phone = '13713529579';
```

结果能查到，但你根本看不出它是怎么找到的。要“看到过程”，用 `EXPLAIN`：

```sql
EXPLAIN SELECT * FROM mall_user WHERE phone = '13713529579';
```

本机真实输出：

```
+----+-------------+-----------+------------+------+---------------+------+---------+------+--------+----------+-------------+
| id | select_type | table     | partitions | type | possible_keys | key  | key_len | ref  | rows   | filtered | Extra       |
+----+-------------+-----------+------------+------+---------------+------+---------+------+--------+----------+-------------+
|  1 | SIMPLE      | mall_user | NULL       | ALL  | NULL          | NULL | NULL    | NULL | 299124 |    10.00 | Using where |
+----+-------------+-----------+------------+------+---------------+------+---------+------+--------+----------+-------------+
```

## 1.4 结果：看懂 EXPLAIN 最重要的 4 个字段

先盯这 4 列，其它以后再说：

| 字段 | 上面结果 | 含义 | 好坏 |
|------|---------|------|------|
| **type** | `ALL` | 访问类型。`ALL`=全表扫描，一行行翻 30 万行 | 😱 最差 |
| **key** | `NULL` | 实际用了哪个索引。`NULL`=一个都没用上 | 😱 没有索引 |
| **rows** | `299124` | 预估要扫描的行数 | 越大越慢 |
| **Extra** | `Using where` | 附加信息。`Using where`=先全表扫完再过滤 | 说明没利用索引定位 |

MySQL 此刻的真实动作：

```
从第 1 行翻到第 300000 行（全表扫）
   → 每一行都比对 phone 是否等于 '13713529579'
   → 一共比了约 29.9 万次，才找到 1 行
```

本机实测这段查询稳定在 **70ms 左右**（30 万行还能接受；换成 1000 万行就是秒级）。

> 顺带认识其余字段（2 秒版，不展开）：
> `id` 执行顺序号；`select_type` SIMPLE=简单查询(非子查询/union)；
> `table` 查哪张表；`possible_keys` 理论上可能用的索引；
> `key_len` 用了索引前缀多少字节；`ref` 用什么值和索引比较；
> `filtered` 扫完后还要再过滤的比例；`partitions` 分区（本教程未用分区）。

## 1.5 操作②：CREATE INDEX 建索引（本阶段最关键一步）

```sql
CREATE INDEX idx_user_phone ON mall_user (phone);
```

逐词解释：

| 词 | 含义 |
|----|------|
| `CREATE INDEX` | 创建索引（DDL 语句） |
| `idx_user_phone` | 索引名。规范：`idx_表名_字段名`，一看就懂 |
| `ON mall_user (phone)` | 给 mall_user 表的 phone 字段建 |

**为什么建在 phone 上？（这是比语法更重要的能力）**
- phone 是高频 `WHERE` 条件列（客服查询、登录、风控都会用）；
- phone 区分度极高：30 万里几乎每行一个值 → 索引能把“30 万选 1”变成“定位 1 行”；
- 区分度低的列（如 status 只有 5 种值）后面阶段 2 会证明：建了也基本没用。

确认一下索引真的建出来了：

```sql
SHOW INDEX FROM mall_user;
-- 会看到 PRIMARY、uk_username、idx_user_phone 三条
```

## 1.6 操作③：同样一句 SQL 再查 + 再 EXPLAIN

```sql
SELECT * FROM mall_user WHERE phone = '13713529579';   -- 结果一样，但过程变了

EXPLAIN SELECT * FROM mall_user WHERE phone = '13713529579';
```

本机真实输出：

```
+----+-------------+-----------+------------+------+----------------+----------------+---------+-------+------+----------+-------+
| id | select_type | table     | partitions | type | possible_keys  | key            | key_len | ref   | rows | filtered | Extra |
+----+-------------+-----------+------------+------+----------------+----------------+---------+-------+------+----------+-------+
|  1 | SIMPLE      | mall_user | NULL       | ref  | idx_user_phone | idx_user_phone | 83      | const |    1 |   100.00 | NULL  |
+----+-------------+-----------+------------+------+----------------+----------------+---------+-------+------+----------+-------+
```

## 1.7 对比：前后两张 EXPLAIN，看懂了就学会索引了

| 字段 | 建索引前 | 建索引后 | 含义变化 |
|------|---------|---------|---------|
| type | `ALL` | `ref` | 全表扫描 → 按索引等值定位 |
| key | `NULL` | `idx_user_phone` | 没索引 → 真的用上了索引 |
| rows | `299124` | `1` | 预估扫描 **29.9 万行 → 1 行** |
| Extra | `Using where` | `NULL` | 过滤工作交给索引完成，不再“扫完再筛” |
| 耗时 | ~70ms | ~20ms（含连接开销，服务器端 1ms 级） | 量级差异 |

**MySQL 建索引后是怎么工作的？**

```
用户输入 phone = '13713529579'
   → 走 idx_user_phone 这棵 B+ 树（按 phone 排序）
   → 二分定位到目标叶子页（约 3~4 层）
   → 叶子节点里存着 (phone, 主键id)
   → 拿着主键 id 回主键索引取完整行（这叫“回表”，阶段 4 细讲）
   → 返回 1 行
```

> 为什么耗时看起来只快了 3 倍？因为命令行客户端有约 15~20ms 的“连接 MySQL”
> 固定开销。**真正的证据是 rows：299124 → 1**，这正是服务器扫描量级的差距。
> 阶段 6 会用慢日志的 `Rows_examined` 看到服务器端真实差异（100万 → 50 行）。

## 1.9 阶段小结

**我学会了什么**
- 没索引时 MySQL 全表扫（EXPLAIN 的 `type=ALL, key=NULL, rows≈30万`）；
- `EXPLAIN` 四字段是判断索引是否生效的“体检报告”：type / key / rows / Extra；
- `CREATE INDEX 索引名 ON 表(列)` 建索引；建索引前先问“这列高频查询吗？区分度高吗？”；
- 同一个 SQL，建索引前后 rows 从 30 万变 1，这就是“索引生效”的硬证据。

**日常开发怎么用**
- 写任何一条可能慢的 SQL，先 `EXPLAIN` 再看结果，别靠感觉；
- 发现 `type=ALL` 且表大 → 检查 WHERE 条件列有没有索引、建得对不对；
- 索引不是写了就完事，用 EXPLAIN 复核它真的被用上。

**面试怎么答**
- Q：怎么判断一条 SQL 有没有走索引？→ 用 EXPLAIN，重点看 type（ALL→全表扫）、key（NULL→没走索引）、rows（预估扫描行数）、Extra。
- Q：索引为什么能快？→ 把列按序排成一棵 B+ 树，查询从“30 万次比对”变成“树上一段二分定位”，复杂度从 O(N) 降到 O(logN)。

**一句话记忆锚点**：`EXPLAIN 里 type 从 ALL 变 ref、rows 从 30 万变 1 —— 索引生效了。`

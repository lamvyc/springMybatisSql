# Java 后端开发 MySQL 索引实战速查表

> 一张表/一张流程图搞定“什么时候建、怎么建、怎么判断生效、慢 SQL 怎么查”。
> 配合前六阶段使用，日常开发直接抄。

## 1. 一条业务 SQL，要不要建索引？(决策流)

```
拿到一条业务 SQL
   │
   ├─ 表只有几千行? ────────────► 不建（全表扫 1ms 内）
   │
   ├─ WHERE/ORDER BY 有列吗?
   │    没有(全表统计/报表) ────► 看有没有覆盖索引可扫，否则评估规模
   │
   ├─ 条件列区分度高吗?
   │    SELECT COUNT(DISTINCT col)/COUNT(*) 越接近 1 越好
   │    低(状态/性别)──────────► 单列索引没用；考虑联合索引的靠后位置
   │
   ├─ 是高频接口吗? ────────────► 低频查询别为它加索引
   │
   └─ 高频 + 高区分度 + 大表
        ├─ 等值 = ?      → 放联合索引前面
        ├─ 范围 BETWEEN  → 放中间（它后面的列无法用于排序）
        ├─ ORDER BY 列    → 放最后一位，省 filesort
        └─ SELECT 列      → 高频列表可把需要的列塞进索引做覆盖
```

## 2. 索引增删查（语法速查）

```sql
-- 建索引
CREATE INDEX idx_orders_user_status_ct ON mall_order (user_id, status, create_time);
CREATE UNIQUE INDEX uk_xxx ON t (col);          -- 唯一索引
ALTER TABLE t ADD INDEX idx_x (col);             -- 等价写法
-- 删索引（MySQL 8 不支持 IF EXISTS，重复执行会报错：先 SHOW INDEX 确认）
DROP INDEX idx_orders_user_status_ct ON mall_order;
ALTER TABLE t DROP INDEX idx_x;
-- 看表的所有索引 / 索引列顺序 / 基数
SHOW INDEX FROM mall_order;
-- 大批量导数据后刷新统计，否则 EXPLAIN rows 失真
ANALYZE TABLE mall_order;
```

索引命名规范：`idx_表名_字段1_字段2`、唯一索引 `uk_表名_字段`。

## 3. EXPLAIN 只看这 4+2 列

| 列 | 值 | 含义 | 判断 |
|----|-----|------|------|
| **type** | const > ref > range > index > ALL | 访问类型 | `ALL`=全表扫，要警惕 |
| **key** | 索引名 / NULL | 真正用到的索引 | NULL=没走索引（possible_keys 里有≠用上） |
| **rows** | 数字 | 预估扫描行数 | 和表行数对比看数量级 |
| **Extra** | 见下 | 附加信息 | filesort/temporary 要警惕 |
| key_len | 字节数 | 用了索引前缀多长 | 变长=少用了索引列 |
| filtered | % | 扫完后还要过滤的比例 | 越低越说明索引没吃全条件 |

Extra 速记：
- `Using filesort` → 排序自己做，试试把 ORDER BY 列放进索引；
- `Using temporary` → 用了临时表（GROUP BY/去重常见），关注；
- `Using index` → **覆盖索引**，不用回表 ✅；
- `Using index condition` → ICP 索引下推，≠覆盖；
- `Backward index scan` → 倒着读索引满足 DESC 排序 ✅。

## 4. 联合索引列序（最左前缀实操版）

```
(a, b, c) 能用：a ✅   a,b ✅   a,b,c ✅
          不能用：b ❌   b,c ❌   a,c ⚠️(只用到 a，c 顺序失效)
列序规则：等值列(区分度高的在前) → 范围列 → 排序列
前缀复用：(user_id,status,create_time) 同时服务 user_id 查询、user_id+status 查询、
          user_id+status+按时间排序 三种形态 —— 旧的 (user_id) 可删掉避免冗余
```

## 5. 索引失效 5 大场景（写 SQL 前扫一眼）

| 场景 | 错误写法 | 修法 |
|------|---------|------|
| 列上套函数 | `WHERE DATE(create_time)=...` | 改区间 `create_time >= ... AND < ...` |
| 隐式类型转换 | 字符串列 `phone = 137...`(数字) | 传字符串 `'137...'` |
| LIKE 前导通配 | `LIKE '%1371%'` | 前缀 `LIKE '1371%'`；真包含需求上 ES |
| 破坏最左前缀 | 联合索引没从第一列用起 | 带上最左列 或 为该形态补新索引 |
| OR 乱拼 | `a=1 OR b=2`，b 无索引 | 两边都建索引 / 改 `UNION ALL` |

## 6. 回表 vs 覆盖索引

```
二级索引叶子 = (索引列..., 主键id)        ← 没有其它列！
要返回的列不在索引里 → 拿主键回聚簇索引取整行 = 回表
Extra 出现 Using index = 覆盖索引，不用回表
列表 SQL：按需写列、少用 SELECT *（* = 强制回表 + 阻断覆盖索引）
```

## 7. 慢 SQL 排查 7 步（生产流程）

```
① 复现并抓到慢 SQL（慢日志/应用日志）
② EXPLAIN：type / key / rows / Extra
③ 定位：没索引？还是索引与 SQL 形态不匹配？(对照失效5大场景)
④ 修复：优先改 SQL；确需索引则按最左前缀设计列序
⑤ 再 EXPLAIN：rows 数量级是否下降、filesort 是否消失
⑥ 验证：慢日志 Query_time / Rows_examined 前后对比
⑦ 回归：SHOW INDEX + 相邻查询各 EXPLAIN，确认无影响

慢日志开关（用完记得关）：
SET GLOBAL slow_query_log = ON;
SET GLOBAL long_query_time = 0.5;    -- 秒
SET GLOBAL slow_query_log = OFF;
SHOW VARIABLES LIKE 'slow_query_log_file';
```

## 8. 面试高频题一句话答案

| 问题 | 一句话答案 |
|------|-----------|
| 索引为什么能提速？ | 排好序的 B+ 树把全表扫 O(N) 变成二分定位 O(logN)，且有序结构天然支持范围/排序 |
| 为什么用 B+ 树不用哈希？ | 哈希只支持等值；B+ 树矮胖、扇出大，支持范围查询与排序（联合索引有序） |
| 什么列适合建索引？ | 高频查询 + 区分度高（COUNT(DISTINCT)/COUNT(*)≈1）；低区分度列没用 |
| 什么是联合索引/最左前缀？ | 多列联合排序的索引；必须从最左列连续取前缀才能用 |
| 联合索引列序怎么定？ | 等值列在前（区分度高的优先），范围/排序列在后 |
| 什么是回表？ | 二级索引不含全部列，拿主键再回主键索引取整行 |
| 什么是覆盖索引？ | 查询所需列都在索引里，EXPLAIN 显示 Using index，不回表 |
| 为什么少用 SELECT *？ | 强制回表、IO 放大、阻断覆盖索引 |
| 哪些写法会让索引失效？ | 函数、隐式类型转换、LIKE 前导通配、不满足最左前缀、OR 带无索引列 |
| 索引越多越好吗？ | 不是：每个索引都增加写放大与空间占用，只服务真实高频查询 |
| 慢 SQL 怎么排查？ | EXPLAIN 四字段定位 → 改 SQL 或补索引 → 再 EXPLAIN → 慢日志验证 → 回归 |
| 深分页怎么优化？ | offset 越大越慢；改游标分页 `WHERE (a,b) < (上一页最后一条) LIMIT n` |

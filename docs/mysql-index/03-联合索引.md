# 阶段 3：联合索引

> 目标：亲手把索引从 `(user_id)` 一路升级到 `(user_id, status, create_time)`，
> 通过每一步 EXPLAIN 的变化理解：**联合索引是什么、列序怎么设计、最左前缀是什么、
> WHERE + ORDER BY 怎么吃进一个索引**。
>
> 配套脚本：`sql/03_联合索引.sql`；业务接口：`GET /api/index-demo/my-orders?userId=29997&status=1`

## 3.1 知识地图

```
联合索引（本阶段，L1 必须掌握）
├─ 是什么       → 多列拼成一个“复合排序目录”，本质还是 B+树
├─ 列序设计     → 等值列在前，排序/范围列在后
├─ 最左前缀     → (a,b,c) 能用 a / a,b / a,b,c；b、b,c 用不上
└─ WHERE+ORDER BY → 排序列进索引 = 干掉 filesort
```

## 3.2 问题：真实接口“我的订单列表”

```sql
SELECT id, order_no, user_id, status, pay_amount, create_time
FROM mall_order
WHERE user_id = ? AND status = ?          -- 两个过滤条件
ORDER BY create_time DESC                 -- 还要倒序
LIMIT 20;
```

教学主角：`user_id = 29997`，他有 53 笔订单（15 笔已支付）。你的库里也可以任选一个用户。

## 3.3 第 0 步：不建索引 —— 100 万行全表扫

```sql
EXPLAIN SELECT id, order_no, user_id, status, pay_amount, create_time
FROM mall_order
WHERE user_id = 29997 AND status = 1
ORDER BY create_time DESC
LIMIT 20;
```

真实结果（关键列）：

```
type = ALL    key = NULL    rows = 996250
Extra = Using where; Using filesort
```

- `Using filesort`：MySQL 把命中的行再额外排一次序；
- 本机实测耗时：**244 / 186 / 189 ms**（每次都全表扫 100 万行）。

## 3.4 第 1 步：先建单列索引 `(user_id)`

```sql
CREATE INDEX idx_user_id ON mall_order (user_id);
```

**只按 user_id 查**（不看 status 时）：

```
type = ref   key = idx_user_id   rows = 53
Extra = Using filesort
```

✅ 53 行一步定位。⚠️ 但 ORDER BY create_time 仍然 filesort（索引里只有 user_id）。

**带上 status=1 再查**（我们要的真实 SQL）：

```
type = ref   key = idx_user_id   rows = 53   filtered = 10.00
Extra = Using where; Using filesort
```

单列索引只处理了 user_id：53 行是“他全部订单”，status=1 还得在行上再过滤，
create_time 还得自己排序。**一个条件一个索引，是不够的。**

## 3.5 第 2 步：升级成 `(user_id, status)`

```sql
DROP INDEX idx_user_id ON mall_order;                -- 旧索引被新索引“前缀包含”，删掉
CREATE INDEX idx_user_status ON mall_order (user_id, status);
```

真实结果：

```
type = ref   key = idx_user_status   key_len = 9   ref = const,const   rows = 15
Extra = Using filesort
```

- `key_len=9`：8(user_id 的 BIGINT) + 1(status 的 TINYINT)，两个条件都吃进索引了；
- `ref = const,const`：两个等值条件都来自常量；
- `rows` 从 53 → 15：status 过滤也交给索引了；
- ⚠️ **filesort 还在**：create_time 不在索引里，排序还得自己做（15 行排序很轻，但后面会让你看它消失）。

## 3.6 第 3 步：升级成 `(user_id, status, create_time)` —— filesort 消失

```sql
DROP INDEX idx_user_status ON mall_order;
CREATE INDEX idx_user_status_ct ON mall_order (user_id, status, create_time);
```

真实结果：

```
type = ref   key = idx_user_status_ct   rows = 15
Extra = Backward index scan          ← Using filesort 不见了！
```

**这就是“WHERE + ORDER BY 吃进一个联合索引”的样子：**

```
索引内部顺序：(user_id, status, create_time) 都按升序排
user_id=29997 且 status=1 的那些行，
   在索引里已经按 create_time 从早到晚排好了
查询要 create_time DESC → 从索引“尾巴往前读”即可
Extra 的 Backward index scan 就是“倒着读索引”
→ 排序工作由索引完成，filesort 直接消失
```

本机实测耗时：**33 / 22 / 21 ms**（对比无索引 244 / 186 / 189 ms，约 8~10 倍）。

## 3.7 亲手验证“最左前缀”

**验证 1：中间列缺失时，第三列的顺序能力也没了**

```sql
EXPLAIN SELECT ... FROM mall_order
WHERE user_id = 29997                    -- 只有第一列，没有中间的 status
ORDER BY create_time DESC LIMIT 20;
```

真实结果：`type = ref, rows = 53, Extra = Using filesort`

原因：索引把行按 `(user_id, status, create_time)` 排序。同一个 user_id 下，
得先按 status 分组、每组内 create_time 才有序。status 没给等值条件，
create_time 的“有序性”就无法保证 → 排序只能 filesort。
（只能用到 user_id 这一个前缀列。）

**验证 2：跳过第一列，索引用都别想用**

```sql
EXPLAIN SELECT ... FROM mall_order
WHERE status = 1
  AND create_time BETWEEN '2024-06-01' AND '2024-06-30'
ORDER BY create_time DESC LIMIT 20;
```

真实结果：`type = ALL, key = NULL, rows = 996250, Extra = Using where; Using filesort`

最左列 user_id 不在条件里 → 整个联合索引用不上，直接全表扫 100 万行。

**最左前缀原则**（写成你能直接抄的结论）：

```
联合索引 (a, b, c) 相当于同时预备了三棵“前缀索引”：
    可用：a            ✅
    可用：a, b         ✅
    可用：a, b, c      ✅
    不可用：b          ❌（没从最左开始）
    不可用：b, c       ❌
    半可用：a, c       ⚠️（a 定位成功；c 因中间 b 缺失无法保证有序）
```

## 3.8 为什么列序是 (user_id, status, create_time)？

| 设计规则 | 本例 |
|---------|------|
| **等值条件放前面**（=） | `user_id = ?`、`status = ?` 都放索引前列 |
| **排序/范围条件放后面** | `create_time` 用于排序，放最后一位才能利用索引顺序 |
| 一列多用：前缀可复用于其它查询 | `(user_id,status,create_time)` 同时服务“只看 user_id”“user+status”“user+status+排序”三种 SQL 形态 |

反例思考：如果建成 `(status, create_time, user_id)`，那么：
- “我的订单”SQL 没带 status 的最左列？带了（user_id 不是最左）→ 直接失效；
- 运营按 status+时间查倒是能用（阶段 5/6 会看到，那其实是**另一种查询形态**，
  需要它自己的联合索引，不能指望一个索引包打天下）。

## 3.10 阶段小结

**我学会了什么**
- 联合索引 = 多列拼成一个有序目录，能同时服务多个等值/排序条件；
- 一个真实查询（两个 WHERE + 一个 ORDER BY）从单列索引一路升级到三列索引的完整过程；
- Extra 里 `Using filesort` 消失、出现 `Backward index scan` = 排序交给了索引；
- 最左前缀：只有“从第一列开始连续取前缀”的查询才能用上联合索引。

**日常开发怎么用**
- 拿到高频 SQL，先把条件分三类：等值 `=` / 范围 `BETWEEN,>,<` / 排序 `ORDER BY`；
- 列序：等值列按区分度从高到低排 → 范围列 → 排序列（范围列之后的列基本“浪费”）；
- 旧索引如果被新联合索引的前缀覆盖（如 idx_user_id 被 idx_user_status_ct 覆盖），删旧留新。

**面试怎么答**
- Q：什么是联合索引/最左前缀？→ 多列联合排序的 B+树；(a,b,c) 只有按 a→b→c 连续取前缀的查询才能用。
- Q：联合索引列序怎么定？→ 等值条件在前，其次区分度高的；范围/排序在后；ORDER BY 列放最后可以免 filesort。
- Q：建了 (a,b) 还有必要建 (a) 吗？→ 没必要，(a) 是 (a,b) 的前缀，会冗余。

**一句话记忆锚点**：`联合索引像按“姓氏→名字→生日”排的电话本：从头连续翻才找得到；等值在前、排序殿后。`

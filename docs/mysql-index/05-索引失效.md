# 阶段 5：索引失效

> 目标：**亲手**制造 5 类最常见的索引失效，再亲手修复。
> 每个场景都按企业排查套路走一遍：错误 SQL → EXPLAIN → 分析 → 改 SQL/索引 → 再 EXPLAIN → 对比。
>
> 配套脚本：`sql/05_索引失效.sql`

## 5.0 总览：索引“失效”的本质

B+ 树能加速的前提是：**能用列本身的顺序做二分**。
只要 MySQL 无法直接比较“索引列的原值”，索引就白建了。五大场景全是这个原因：

| # | 场景 | 本质 |
|---|------|------|
| ① | 对索引列使用函数 | 要比较的是“算出来的值”，不是列原值 |
| ② | 隐式类型转换 | 给列偷偷套了 CAST()（同①） |
| ③ | LIKE '%xxx' | 开头是通配符，不知道从树哪里二分 |
| ④ | 不满足最左前缀 | 联合索引必须从最左列开始用 |
| ⑤ | OR 条件 | 有一个分支用不上索引，整句退化为全表扫 |

## 5.1 场景①：对索引列使用函数

**背景 SQL**：后台要查“2024-06-15 当天下的订单”。新手容易写成：

```sql
-- 先保证 create_time 有索引
CREATE INDEX idx_ct ON mall_order (create_time);

EXPLAIN SELECT id, order_no, user_id, status, pay_amount, create_time
FROM mall_order
WHERE DATE(create_time) = '2024-06-15'
LIMIT 20;
```

**错误结果（真实）**：`type = ALL, key = NULL, rows ≈ 996250, Extra = Using where`

**原因**：索引里存的是 `create_time` 原值，不是 `DATE(create_time)` 算出来的值。
想比较，只能把每一行的 create_time 先算一遍 → 索引顺序完全派不上用场 → 全表扫。

**修复（改 SQL，不改业务语义）**：把函数从列上挪走，写成半开区间：

```sql
EXPLAIN SELECT id, order_no, user_id, status, pay_amount, create_time
FROM mall_order
WHERE create_time >= '2024-06-15 00:00:00'
  AND create_time <  '2024-06-16 00:00:00'
LIMIT 20;
```

**修复后（真实）**：`type = range, key = idx_ct, rows = 1381, Extra = Using index condition`

| 对比 | type | key | rows |
|------|------|-----|------|
| 错误 SQL | ALL | NULL | 996250 |
| 改范围 | range | idx_ct | 1381 |

> 顺手清理：`DROP INDEX idx_ct ON mall_order;`

## 5.2 场景②：隐式类型转换

**背景 SQL**：`mall_user.phone` 是 **VARCHAR**（存的是字符串）。
很多代码把手机号当数字传（Java 里被解析成 long 很常见）：

```sql
CREATE INDEX idx_user_phone ON mall_user (phone);   -- 保证 phone 有索引

EXPLAIN SELECT * FROM mall_user WHERE phone = 13713529579;   -- 注意：数字，没有引号
```

**错误结果（真实）**：

```
type = ALL    possible_keys = idx_user_phone    key = NULL    rows ≈ 299124
```

**原因**：MySQL 遇到“字符串列 = 数字”，规则是**把列转成数字**再比（而不是把数字转字符串）。
转列 = 给列套了个隐式 `CAST(phone AS ...)` —— 和场景①一样，索引失效。
注意 `possible_keys` 里明明有 idx_user_phone，但 `key` 是 NULL：**“可能用”≠“用上”**。

**修复（改 SQL）**：传字符串：

```sql
EXPLAIN SELECT * FROM mall_user WHERE phone = '13713529579';
```

**修复后（真实）**：`type = ref, key = idx_user_phone, rows = 1`

| 对比 | type | key | rows |
|------|------|-----|------|
| phone = 数字 | ALL | NULL | 299124 |
| phone = '字符串' | ref | idx_user_phone | 1 |

> 应用层口诀：**字段是 VARCHAR，参数就传字符串**（MyBatis 里注意 Java 类型别把 phone 映射成 long）。

## 5.3 场景③：LIKE '%xxx' 前导通配

**背景 SQL**：运营想按手机号“号段”找人，比如 `1371` 开头。

```sql
-- ✓ 前缀匹配：'1371%' 相当于范围 [1371, 1372)
EXPLAIN SELECT id, username, phone FROM mall_user WHERE phone LIKE '1371%';
-- type = range, key = idx_user_phone, rows = 324, Extra = Using index condition
```

**错误 SQL**：前导通配 `'%1371%'`（“包含”语义）：

```sql
EXPLAIN SELECT id, username, phone FROM mall_user WHERE phone LIKE '%1371%';
```

**错误结果（真实）**：`type = ALL, key = NULL, rows ≈ 299124`

**原因**：B+ 树按“前缀”排序。`%` 在开头时，MySQL 不知道应从树的哪个分支开始二分，
只能全表逐行 LIKE。

| 对比 | type | key | rows |
|------|------|-----|------|
| LIKE '1371%' | range | idx_user_phone | 324 |
| LIKE '%1371%' | ALL | NULL | 299124 |

**修复思路**：
- 业务允许 → 改成前缀匹配 `'1371%'`；
- 业务必须是“任意位置包含” → 普通 B+ 树索引救不了，上 ES / 分词 / 全文索引。

## 5.4 场景④：联合索引不满足最左前缀

**背景**：线上有“我的订单”索引 `(user_id, status, create_time)`。
运营后台的 SQL 却是“状态 + 时间段”（**没带 user_id**）：

```sql
CREATE INDEX idx_user_status_ct ON mall_order (user_id, status, create_time);

EXPLAIN SELECT id, order_no, user_id, status, pay_amount, create_time
FROM mall_order
WHERE status = 1
  AND create_time BETWEEN '2024-06-01 00:00:00' AND '2024-06-30 23:59:59'
ORDER BY create_time DESC
LIMIT 20;
```

**错误结果（真实）**：`type = ALL, key = NULL, rows ≈ 996250, Extra = Using where; Using filesort`

**原因**：联合索引最左列是 user_id，条件里没有它 → 索引整个用不上（阶段 3 的最左前缀）。

**修复有两个方向，先想清楚你的业务**：

方向一（改 SQL）：业务本身能带上 user_id（如“查某个用户在某状态某时间的单”）：

```sql
EXPLAIN SELECT ... FROM mall_order
WHERE user_id = 29997
  AND status = 1
  AND create_time BETWEEN '2024-06-01 00:00:00' AND '2024-06-30 23:59:59'
ORDER BY create_time DESC LIMIT 20;
```

方向二（改索引）：如果“按状态+时间段”是另一种**真实高频查询形态**，就该为它建索引：

```sql
CREATE INDEX idx_order_status_ct ON mall_order (status, create_time);

EXPLAIN SELECT id, order_no, user_id, status, pay_amount, create_time
FROM mall_order
WHERE status = 1
  AND create_time BETWEEN '2024-06-01 00:00:00' AND '2024-06-30 23:59:59'
ORDER BY create_time DESC
LIMIT 20;
```

**修复后（真实）**：`type = range, key = idx_order_status_ct, rows ≈ 39158,
Extra = Using index condition; Backward index scan`

| 对比 | type | key | rows | Extra |
|------|------|-----|------|-------|
| 只有 (user_id,status,create_time) | ALL | NULL | 996250 | Using filesort |
| 新增 (status,create_time) | range | idx_order_status_ct | 39158 | 无 filesort |

> 这正是阶段 6 线上事故的“标准答案”——同一张表，两种查询形态，各配各的索引。

## 5.5 场景⑤：OR 条件

**背景 SQL**：`username = 'user_1'`（有唯一索引）**OR** `email = 'user2@example.com'`（没索引）：

```sql
EXPLAIN SELECT id, username, phone, email
FROM mall_user
WHERE username = 'user_1' OR email = 'user2@example.com';
```

**错误结果（真实）**：`type = ALL, rows ≈ 299124`（possible_keys 只有 uk_username，key=NULL）

**原因**：OR 的语义是“满足任意一个就算”，MySQL 想让两边都高效就得分别走索引再合并
（index_merge）。但 email 那半边没索引 → 合并做不成 → 整个查询退化成全表扫。
**一个分支拖垮整句，这就是 OR 的坑。**

**修复方向一（补索引）**：两边都有索引后，MySQL 可以做 index_merge：

```sql
CREATE INDEX idx_user_email ON mall_user (email);

EXPLAIN SELECT id, username, phone, email
FROM mall_user
WHERE username = 'user_1' OR email = 'user2@example.com';
-- type = index_merge, Extra = Using union(uk_username, idx_user_email)
```

**修复方向二（推荐，SQL 改造）**：UNION ALL 拆成两条，各自清爽地走自己的索引：

```sql
EXPLAIN
SELECT id, username, phone, email FROM mall_user WHERE username = 'user_1'
UNION ALL
SELECT id, username, phone, email FROM mall_user WHERE email = 'user2@example.com';
-- 第一段 type=const(uk_username)，第二段 type=ref(idx_user_email)，rows 各为 1
```

| 对比 | type | 说明 |
|------|------|------|
| OR（email 无索引） | ALL | 30 万行全扫 |
| OR（email 补索引） | index_merge | 两个索引各查 1 行再 union |
| UNION ALL 拆分 | const + ref | 两段各自最优 |

> 清理演示索引：`DROP INDEX idx_user_email ON mall_user; DROP INDEX idx_order_status_ct ON mall_order;`

## 5.6 阶段小结

**我学会了什么**
- 五类失效场景的错误 SQL 长什么样、EXPLAIN 里什么特征、怎么修；
- “possible_keys 有索引 ≠ 用上了”：真正生效看 key 和 rows；
- 同一句 SQL 的失效与生效，rows 常常是 30 万 vs 1~几千的差距。

**日常开发怎么用**
- 写完 SQL 习惯性 EXPLAIN，见到 `type=ALL` 先按“五类失效”对号入座；
- 代码 Review 盯三点：参数类型（VARCHAR 传字符串）、日期条件（写区间不套函数）、
  OR 拆分（UNION ALL / IN）；
- 新索引上线后跑一遍线上慢 SQL 的 EXPLAIN 做前后对比。

**面试怎么答**
- Q：哪些情况索引会失效？→ 函数、隐式类型转换、LIKE 前导通配、不满足最左前缀、OR 里有索引外的列。
- Q：为什么函数包列就失效？→ 索引存的是列原值，无法用“算出来的值”做二分。
- Q：OR 为什么失效？→ OR 要两边都能走索引再合并；一边不行就整句全表扫，可改 UNION ALL。

**一句话记忆锚点**：`索引只认“原汁原味的列 + 连续可用的前缀”；函数、换型、%开头、断最左、OR 乱拼，统统白建。`
